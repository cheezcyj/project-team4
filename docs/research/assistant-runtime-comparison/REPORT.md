# 모델 서버별 연속·동시 요청 비교

2026-10-23, 사용자가 연 11480 서버와 Ollama를 순서대로 시험했다. **11480의 llama.cpp와 Ollama에서 각각 12개 질문 요청이 모두 HTTP 200을 반환했다.** 자동 재시도는 없었고, JSON 답변 형태와 허용된 출처 ID도 24개 모두 통과했다. 앞서 LM Studio에서 반복된 대기 없는 순차 호출 오류는 이 두 실행에서 재현되지 않았다.

이 결과는 한정된 연결 시험이다. **LM Studio 자체 결함이나 내부 정리 지연이라는 원인을 확정하지 않는다.** 서버별 빌드·슬롯 수·템플릿·기본 샘플링 설정이 다르므로 속도나 품질을 같은 조건의 벤치마크처럼 비교하지 않는다.

## 결과

각 칸은 성공한 질문 수/전송한 질문 수다. 지연 조건은 이전 응답 본문을 끝까지 받은 후 3초를 기다렸으며, 동시 조건은 첫 응답 헤더가 도착하기 전에 4개 요청 모두 전송됐음을 HTTP 진단 기록으로 확인했다.

| 서버 | 실제 설정 | 대기 없는 순차 | 응답 후 3초 대기 | 4개 동시 HTTP 요청 |
| --- | --- | ---: | ---: | ---: |
| 이전 LM Studio `1234` | parallel 4 | 2/4 | 4/4 | 4/4 |
| 사용자 llama.cpp `11480` | **슬롯 1** | **4/4** | **4/4** | **4/4** |
| 별도 Ollama `11435` | **슬롯 4** | **4/4** | **4/4** | **4/4** |

LM Studio에서는 질문 순서를 바꿔도 2·4번째 요청이 HTTP 400 `Engine protocol predict request failed: fetch failed`를 반환했고, 클라이언트 연결을 매번 새로 만들어도 같은 결과였다. 3초 대기와 동시 전송에서는 오류가 없었다. 이번 llama.cpp·Ollama 시험에서도 대기 없는 순차 호출을 포함한 세 조건이 모두 성공했다.

11480은 슬롯을 변경하지 않았다. 따라서 동시 HTTP 요청 4개 성공은 **슬롯 1개인 서버가 요청을 받아 처리했다는 결과**이며, 4개 토큰 디코딩을 동시에 실행했다는 증거로 세지 않는다. Ollama는 실제 엔진 로그의 `n_seq_max=4`와 슬롯 0~3 생성을 확인했다.

## 시간

아래는 4개 질문이 끝날 때까지의 앱 클라이언트 측 경과 시간이다. 토큰 속도나 TTFT가 아니다.

| 서버 | 대기 없는 순차 | 응답 후 3초 대기 | 4개 동시 HTTP 요청 |
| --- | ---: | ---: | ---: |
| 이전 LM Studio | 1.99초, 오류 2개 포함 | 11.29초 | 2.13초 |
| llama.cpp 11480 | 2.11초 | 10.80초 | 1.65초 |
| Ollama 11435 | **25.55초** | 10.86초 | 6.38초 |

Ollama는 빈 프롬프트로 미리 로드한 뒤에도 첫 실제 질문에 **24.39초**가 걸렸다. 이후 순차 요청은 0.30~0.77초, 동시 요청은 각각 5.94~6.38초였다. 첫 요청 지연의 원인은 이 시험에서 따로 분석하지 않았다. 이 값을 숨기거나 정상 상태의 생성 속도로 합산하지 않는다. 기존 11480 모델이 Ollama 시험 중에도 메모리에 남아 있었으며, GPU 메모리·캐시·엔진 설정을 완전히 통제한 성능 비교가 아니다.

## 모델과 서버

- 질문은 이전 실제 전송 원본에서 가져온 G02(기록 메모), G01(당화혈색소), G04(가벼운 운동), G03(무가당) 순서다. 메시지·검색 근거·온도 0.1·최대 512 토큰·비스트리밍·응답 형식 text 등은 유지하고, 각 서버의 모델 라우팅 식별자만 변경했다.
- 11480은 `TurboQuantGUI/engines/tqp/v0.4.0/llama-server.exe`다. `--version` 결과는 **`version: 1 (bcb85fc)`**, MSVC 19.44.35229.0 / Windows AMD64다. 설치 폴더의 이름과 엔진 커밋을 구분한다.
- 11480의 실제 옵션은 context 131072, parallel 1, K/V 캐시 bf16, flash attention auto였다. 기본 top_k 64, top_p 약 0.95, min_p 약 0.05도 관찰했다. 온도와 출력 토큰 제한은 요청 본문으로 지정했다.
- Ollama **0.40.9**를 기존 사용자 서버 11434와 분리해 **11435**에서 실행했다. `OLLAMA_NUM_PARALLEL=4`, `OLLAMA_CONTEXT_LENGTH=131072`, flash attention 켬, K/V 캐시 f16을 사용했다. 엔진은 슬롯당 context 131072, 전체 context 524288과 슬롯 4개를 기록했다. 기존 LM Studio의 context 메타데이터만으로 동일한 전체 KV 할당이었다고 판단하지 않는다.
- Ollama는 현재 GGUF를 로컬로 가져왔다. [공식 GGUF 가져오기 방식](https://docs.ollama.com/import)을 사용했으며 새 모델 다운로드나 재양자화는 하지 않았다. [병렬 설정의 의미](https://docs.ollama.com/faq#how-does-ollama-handle-concurrent-requests)도 실제 엔진 로그와 대조했다.
- 11480이 참조한 원본 GGUF와 Ollama의 가져온 blob은 **5,154,941,280바이트**, SHA-256 **`676c35070db6dbe52f93e9c864ee0fba4eddea94b9c875d9cb10daff453fbaee`**로 일치했다. 예전 LM Studio 시험에서는 당시 GGUF 해시를 별도로 캡처하지 않았다.
- 서버별 템플릿과 기본 sampler는 다르다. Ollama의 실제 로그에는 top_p 1.0, min_p 0.0이 나타났다. 따라서 서버 교체 외의 모든 내부 조건을 일치시킨 실험이라고 주장하지 않는다. 하드웨어 클럭은 사용자가 앞서 기본 상태라고 알려줬으며 이번 스크립트가 독립적으로 측정하거나 변경하지 않았다.

## 실행 범위와 정리

이번 새 시험은 **질문 요청 24회 + Ollama 빈 프롬프트 사전 로드 1회**다. 사전 로드는 빈 응답과 `done_reason=load`를 반환했으며 답변 생성으로 세지 않는다. 서버 메타데이터 조회와 모델 등록은 별도다. 처음 Ollama 준비 시 로그 파일의 비동기 열기 순서 때문에 자식 서버 실행 전에 실패한 시도도 보존했다. 해당 시도에는 모델 로드·질문 요청이 없었고, 준비 코드를 수정한 다음 새 폴더로 실행했다.

시험은 공개 질문·지식만 모델 API에 직접 전달했다. 개인 기록·계정·의료정보를 추가하지 않았으며 앱의 RAG 검색, 자료 요약 보충, 안전 분류, Auth·DB 기능을 다시 평가한 것은 아니다. 24개 성공은 HTTP·JSON·출처 ID 검사 결과이며 독립적인 답변 내용·의료 검토를 뜻하지 않는다.

비교 시험에서는 사용자 서버 11480·11434·1234와 앱 3005에 중지·재시작 명령을 보내지 않았다. 시험 직후에는 네 포트가 열려 있었으나, 마지막 상태 확인에서는 11480·1234가 연결 거부 상태였고 11434·3005만 응답했다. **후속 대화에서 사용자가 직접 모두 종료했다고 확인했다.** 이 마지막 연결 거부를 엔진 장애로 해석하지 않는다. 당시 캡처의 ‘종료 원인 미확인’ 기록과 해시 목록은 그대로 보존한다. 내가 시작한 임시 Ollama 11435와 그 자식 모델 프로세스는 시험 후 종료했다. 가져온 모델은 Git에서 제외된 `.local/assistant-ollama-runtime-20261023-02/models/`에 보존했다. 비교 시험 당시 앱의 `.env.local`, README, 마이그레이션은 수정하지 않았고 커밋·PR도 하지 않았다. 이후 사용자가 Ollama 사용을 선택하여 별도로 [기본 서버 연결](../../ASSISTANT_OLLAMA.md)을 진행했다.

현 시점의 판단은 **LM Studio와 그 실행 구성에 조사 우선순위를 둘 근거가 늘었다**는 것이다. 엔진 빌드와 슬롯·캐시·템플릿 차이를 맞춘 추가 비교 전에는 LM Studio 자체의 원인을 확정할 수 없다. 3초 대기는 관찰된 회피 조건이며 제품 코드에 필수 대기로 추가하지 않았다.

# 현재 개발기획서 정리

기준 문서: [당뇨 혈당관리 웹앱 개발기획서, 개정 1.2](https://docs.google.com/document/d/15rIBxYKsMnxPxZFhEya4zMbj88-NxNsS/edit). 작성일과 이번 열람일은 2026-10-20입니다. 외부 원문은 수정하지 않았습니다.

관련 문서: [당뇨 혈당관리 서비스 시장조사, 개정 1.2](https://docs.google.com/document/d/1UEEty8VKuG5GvY2xzg6rRNwn-eHYoyXX/edit). 시장조사서는 수요·경쟁 서비스·차별화 가설의 근거, 개발기획서는 구현 범위·기술·역할·검증 기준으로 사용합니다.

이 문서는 공유된 기획서와 사용자의 최신 확인 사항을 정리한 로컬 요약입니다. 이전의 음식 검색·영양 계산 중심 제안과 Streamlit·SQLite 제안은 현재 기획 기준에서 대체되었습니다. 서비스 구현은 아직 시작하지 않았습니다.

## 최신 진행 조건과 원문 차이

- 팀원: **3명**. 사용자가 앞선 4명 안내를 정정했습니다.
- 제출 마감: **2026-10-26 오전 10시, 한국 시간**.
- 필수 기술·별도 평가 기준: 없다고 사용자가 전달했습니다.
- 형태: 모바일·PC 반응형 웹앱.
- 참고 서비스: 닥터다이어리.
- 원문은 3인·7일, 시작일 미정, 1인 하루 6시간을 가정합니다. 인원은 최신 확인과 일치하지만 시작일·마감 표기는 실제 일정에 맞춰 수정할 필요가 있습니다.
- 기획서의 기능·WBS·ERD는 계획이며 구현·검증이 완료되었다는 뜻이 아닙니다.

## 시장조사서의 대상과 차별화 가설

시장조사서가 제안하는 초기 대상은 이미 혈당을 측정하고 자신의 수치를 수동으로 정리하려는 성인입니다. 닥터다이어리·파스타·Health2Sync·mySugr의 공개 기능을 비교하며 기본 혈당 입력과 그래프는 기존 서비스에도 있음을 전제로 합니다.

| 가설 | 구현 연결 | 관찰할 결과 |
| --- | --- | --- |
| 필수 입력 항목이 적으면 기록 완료가 쉬울 것이다 | 혈당값·측정시각·측정상황 필수, 식사 메모 선택 | 같은 가상 기록 과제의 성공 여부와 입력 시간 |
| 기록 옆 메모가 과거 기록을 찾는 데 도움이 될 것이다 | 날짜별 목록, 같은 기간 그래프와 메모 | 특정 날짜의 식후 기록·메모 찾기 과제 성공 여부 |
| 변경 결과가 명확하면 저장 여부를 판단하기 쉬울 것이다 | 저장 후 갱신, 수정·삭제 결과와 원본 일치 | 저장·새로고침·수정·삭제 시나리오 통과 여부 |

이 항목은 검증할 가설이며 입증된 경쟁 우위나 혈당 개선 효과가 아닙니다. 사용자 과제 결과를 구현 후 기록합니다. 원문의 시장 통계·경쟁 서비스 기능은 이번에 문서 내용을 확인한 것이며 외부 원출처를 다시 검증한 결과는 아닙니다.

## P0: 기록 관리 흐름

핵심 시나리오는 **로그인 → 최초 이용 동의 → 혈당 기록 → 목록과 최근 7일 그래프 → 수정·삭제 → 재로그인 후 기록 확인**입니다.

| ID | 필수 기능 | 핵심 완료 기준 |
| --- | --- | --- |
| F01 | 로그인·로그아웃 | 사전 발급한 두 테스트 계정으로 인증하고 로그아웃 뒤 보호 화면 접근 차단 |
| F02 | 최초 이용 동의 | 동의 버전·서버 시각 저장, 미동의·버전 불일치 상태에서 기록 저장 차단 |
| F03 | 혈당 등록 | 수치·실제 측정시각·측정상황·선택 식사 메모 저장, 재로그인 후 유지 |
| F04 | 기록 조회 | 측정시각순 목록, 최근 7일·특정 날짜의 반환 행 일치 |
| F05 | 수정·삭제 | 선택한 본인 기록만 변경, 삭제 전 대상 확인, 실패 시 입력 보존 |
| F06 | 최근 7일 그래프 | 원본 측정점을 표시하고 미측정 값을 0이나 예측값으로 채우지 않음 |
| F07 | 사용자별 분리 | 타인 ID·직접 요청으로도 다른 사용자의 기록에 접근 불가 |
| F08 | 반응형·상태 처리 | 모바일·태블릿·PC에서 입력·조회 가능, 로딩·빈 상태·오류·포커스 처리 |

혈당 단위는 mg/dL이며 양의 정수로 받습니다. 측정상황은 `fasting`, `before_meal`, `after_meal_2h`, `other`로 구분하고 식사 메모는 선택 항목, 최대 500자입니다. 입력 형식 검증을 정상·위험 판정으로 사용하지 않습니다.

실제 측정시각과 서버 저장시각을 구분합니다. 화면과 기간 조회는 Asia/Seoul 기준이며 최근 7일은 오늘을 포함한 7개의 달력 날짜입니다. 조회는 시작일 00시 이상·종료일 다음날 00시 미만입니다. 같은 측정시각의 재측정도 허용하고 시각·기록 ID로 안정적으로 정렬합니다.

## 기술과 데이터 구조

기획서의 권장 구성은 **Next.js + TypeScript + Supabase Auth/PostgreSQL + Recharts**입니다. CSS는 팀이 익숙한 방식 또는 Tailwind를 사용하며 버전은 착수 시 고정하는 계획입니다. 아직 실제 기술 구성과 의존성을 설치하지 않았습니다.

| 테이블 | 역할 | 핵심 필드 |
| --- | --- | --- |
| `auth.users` | Supabase 관리형 인증 | `id`, `email`, `created_at` |
| `public.user_consents` | 사용자당 현재 동의 0~1개 | `user_id`, `policy_version`, `agreed_at` |
| `public.glucose_records` | 사용자의 수동 혈당 기록 | `id`, `user_id`, `glucose_mg_dl`, `measured_at`, `measurement_context`, `meal_memo`, `created_at`, `updated_at` |

공개 테이블에는 사용자별 RLS와 입력 제약을 적용합니다. 동의와 기록은 인증 사용자 ID를 참조하며 일반 CRUD가 관리자 권한으로 사용자별 정책을 우회하지 않도록 합니다. 그래프는 별도 통계 테이블 대신 같은 원본 기록에서 구성합니다. 식품·식사·영양소 테이블은 이번 범위에 없습니다.

## 공공데이터와 시연 데이터의 역할

이번 기획서는 **가상 혈당·식사 메모 데이터로 시연**합니다. 현재 P0 구현에는 추가 공공데이터나 예측 모델 학습 자료가 필수가 아닙니다.

| 자료 | 이번 버전에서의 위치 |
| --- | --- |
| 질병관리청 검진·식품섭취·코드북 | 프로젝트 배경 조사, 후속 분석 참고 |
| 공공데이터포털 영양성분 CSV | 후속 음식 검색·영양 계산의 후보 데이터 |
| 가상 혈당·식사 메모 | 두 테스트 계정의 기록·그래프·권한 검증용 |
| CGMacros 등 연속혈당 연구 자료 | 후속 식후 혈당 분석 후보. 현재 수동 기록 MVP에는 불필요 |
| 지역 건강통계·보건기관·공원 | 도시 주제 연결이 추가로 필요할 때 검토할 후보 |

가상 데이터는 0건·1건·여러 건·같은 시각·빠진 날짜·서울 날짜 경계를 검증할 수 있도록 준비합니다. 공공조사 참여자와 서비스 계정을 연결하거나 공공 검진값을 사용자의 반복 측정 기록처럼 사용하지 않습니다.

이번 범위에서 자유 회원가입·복구, 독립 식사·운동·복약 CRUD, 음식 검색·영양 계산, 내보내기, CGM·블루투스, 사진 인식, 모델 학습·의료 AI는 후속 후보입니다.

## 3인 역할과 마감 기준 일정 제안

역할의 기준은 원문과 같습니다. 아래 날짜 배치는 실제 마감에 맞춘 제안이며 원문의 상세 WBS를 수정하거나 실행한 결과가 아닙니다.

| 담당 | 책임 |
| --- | --- |
| A | 로그인·동의 UI, 기록 폼·목록·필터 UI, 등록·수정·삭제와 반응형 |
| B | DB·ERD·입력 제약, Auth·RLS·동의 규칙, 원본 수치 대조 |
| C | 기간 조회·그래프·대시보드, 통합 검증·배포·시연 |

| 날짜 | 도달할 상태 제안 |
| --- | --- |
| 10/20 | P0·필드·기간 규칙 합의, 프로젝트·DB 설정과 기본 배포 |
| 10/21 | 두 테스트 계정 인증·동의, 기록 등록과 재조회 연결 |
| 10/22 | 목록·수정·삭제·기간 조회 통합, 중간 배포 |
| 10/23 | 최근 7일 그래프, 첫 전체 시연과 사용자별 접근 검증 |
| 10/24 | 날짜 경계·입력·실패 상태·반응형 검증과 핵심 결함 수정 |
| 10/25 | 기능 추가 종료, 배포 회귀·실행 재현·발표·공동 리허설 |
| 10/26 | 제출물 최종 확인 및 **10:00 이전 제출** |

원문 공수는 3명 × 7일 × 6시간 = 126인시이며 계획 97인시·예비 29인시입니다. 10/20~25의 6일을 각자 하루 6시간 모두 사용할 수 있다고 가정해도 108인시이고, 동일한 97인시 계획을 유지하면 산술상 예비는 11인시입니다. 실제 가용 시간은 확인되지 않았으므로 이 수치를 확보된 시간으로 간주하지 않습니다. 10/26은 오전 마감이므로 온전한 개발일로 배정하지 않습니다.

## 제출과 검증

두 계정의 데이터 분리, 미동의·동의 버전 불일치, 입력 오류·직접 요청, 서울 날짜 경계, 그래프 0·1건·누락·같은 시각, 저장 실패·세션 만료를 검증합니다. 최종 완료는 실제 저장·재조회·수정·삭제와 배포 환경에서의 핵심 시나리오 실행으로 판단합니다. 현재는 이러한 검증을 수행하기 전입니다.

원문 제출물은 시장조사서·개발기획서·WBS·ERD·실행 가능한 소스·실행 및 환경변수 안내·검증 결과·시연 자료입니다. 시장조사서·개발기획서·WBS·작업기록은 원문에서 저장소 커밋 제외 대상으로 정했습니다. 커밋 메시지의 사전 확인과 커밋·푸시 각각의 실행 직전 승인 절차도 원문에 기재되어 있습니다. 이 로컬 요약과 데이터 출처 보완 작업에서는 커밋·푸시를 실행하지 않았습니다.

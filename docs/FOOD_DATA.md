## 생성·검증·조회

Python 3.10 이상, 추가 패키지 없이 프로젝트 루트에서 실행한다. 음식 CSV만 ZIP에서 읽고 검진·섭취기록을 서비스 회원 자료로 변환하지 않는다.

```powershell
python scripts/food_catalog.py prepare
python scripts/food_catalog.py validate
python scripts/food_catalog.py search "흑미밥" --limit 5
python scripts/food_catalog.py search "김 치 찌 개" --limit 5
python scripts/food_catalog.py nutrition P123-201020300-6723
python scripts/food_catalog.py nutrition P123-201020300-6723 --amount 200 --unit g
```

다른 출력 폴더를 쓸 때는 공통 인수를 하위 명령 앞에 둔다.

```powershell
python scripts/food_catalog.py --data-dir .tmp/research/food-reproduction prepare
python scripts/food_catalog.py --data-dir .tmp/research/food-reproduction validate
```

출력은 UTF-8 JSON이며, CLI에서 한글이 깨지면 `python -X utf8`로 실행한다. 조회 결과는 `catalog_id`와 함께 반환한다. 현재 코드는 JSONL을 메모리에 읽어 조회하는 개발 참고 코드이며 실제 서비스의 검색 인덱스·API·접근 제어를 구현한 것은 아니다.

## 검색 규칙

1. Unicode NFKC·소문자화를 적용하고 검색용 이름에서 공백·밑줄을 제거한다. 예: `김 치 찌 개`로 `김치찌개`를 검색할 수 있다. 원본 이름은 그대로 둔다.
2. 포함 문자열 후보를 구하고, 정규화 이름이 정확히 같은 후보, 이름 앞부분이 일치하는 후보, 나머지 포함 후보 순으로 정렬한다. 같은 순위는 정규화 이름과 식품코드 순으로 고정한다.
3. 응답의 `exact_name_matches`, `match_kind`로 정확한 이름과 관련 후보를 구분한다. 첫 결과를 자동으로 먹은 음식으로 선택하지 않는다.
4. 기본 10개, 최대 50개 결과와 `offset`, `returned_count`, `has_more`를 제공한다. 후보마다 코드·이름·음식 구분·기준량·제공기관을 표시한다.
5. 동의어·오타·음식 의미 추론은 구현하지 않았다. 빈 검색어는 오류, 없는 검색어는 빈 후보 목록으로 처리한다.

| 검색어 | 정확한 이름 일치 | 관련 후보 포함 전체 | 해석 |
| --- | ---: | ---: | --- |
| 흑미밥 | 5 | 26 | 같은 이름의 여러 코드와 흑미밥이 포함된 다른 제품을 구분 |
| 김치찌개 | 5 | 65 | 조리법·단위가 다른 후보를 사용자가 선택 |
| 우유 | 0 | 245 | 공백·밑줄 정리 후 결과. 이름에 우유가 포함된 제품을 일반 우유로 단정하지 않음 |
| 바나나 | 0 | 256 | 관련 빵·음료 등 후보를 생과일 바나나와 동일하게 보지 않음 |

가공 전 문자열에 단순히 `우유`가 포함된 행은 242개였고, 검색용 공백·밑줄 정리 후에는 245개다. 행을 추가한 것이 아니라 같은 5만 행에서 검색되는 후보 범위가 달라진 것이다.

## 영양정보 조회·환산 규칙

- **양 미입력:** 원본 기준량의 값을 그대로 반환한다. 실제 섭취량으로 표현하지 않는다.
- **양 입력:** 양과 단위를 함께 받아 `성분 × 입력량 / 기준량`을 계산한다. 숫자는 유한한 양수, 단위는 g 또는 ml여야 한다.
- **단위:** 같은 g끼리 또는 같은 ml끼리 계산한다. g/ml가 다르거나 `1공기`처럼 확인되지 않은 단위면 오류로 안내한다. `mL`는 `ml`로 인식한다.
- **결측·0:** 빈 영양소는 null과 `missing_nutrients`로 반환한다. 실제 0은 0을 유지한다. `값 || 0` 같은 처리로 결측을 지우지 않는다.
- **반올림:** 원본 데이터와 기준량 조회의 수치는 보존한다. 환산 결과만 소수 둘째 자리까지 `ROUND_HALF_UP`으로 반올림한다.
- **합계:** 현재 참고 코드는 선택한 음식 1개를 조회·환산한다. 식사 전체나 하루 총량을 계산한 결과로 확장하지 않는다.

검증용 예시는 다음과 같다. 실제 섭취·식단 권고가 아니라 원본값에 대한 산술 확인이다.

| 입력 | 기대 결과 |
| --- | --- |
| `P123-201020300-6723`, 양 없음 | 100g 기준 열량 145kcal, 탄수화물 31g |
| 위 코드, 200g | 열량 290kcal, 탄수화물 62g, 단백질 6g, 지방 1.6g |
| 위 코드, 200g | 당류·나트륨은 실제 0을 유지, 식이섬유는 null 유지 |
| `D706-266000000-0001`, 250ml | 열량 47.5kcal, 탄수화물 5.83g, 지방 1.33g, 나트륨 475mg |
| `D501-052000000-0001`, 200g | 원본은 100ml이므로 `unit_mismatch` |

## 데이터 확인 결과와 남은 제약

- 50,000개 식품코드, 이름 41,754개. 이름이 중복되는 경우 4,215개를 합치지 않고 보존했다.
- 기준량 100g 40,653행 / 100ml 9,347행. 음식 17,732행 / 가공식품 32,268행이다.
- 빈 값은 지방 11,684, 탄수화물 11,158, 당류 123, 식이섬유 44,793, 나트륨 63개다. 식품중량 1,895개도 null로 보존했다.
- **흑미밥 코드 `D501-052000000-0001` 등 일부의 원본 기준량이 100ml로 기록되어 있다.** 이 작업에서 100g으로 고치거나 밀도를 추정하지 않았다. 정확한 원자료와의 대조가 필요한 사례로 manifest에 남겼다.
- 추가 대조(2026-10-21): 보유한 [음식 DB 엑셀](<../data/20260828_음식DB_19617건.xlsx>)에서도 `D501-052000000-0001`, `D601-052000000-0001`, `D701-052000000-0001`의 기준량이 모두 100ml이며 식품중량도 각각 250ml·310ml·390ml로 CSV와 일치했다. 따라서 이 3건을 CSV 추출 과정의 단위 오류로 판단할 근거는 없다. 엑셀이 공식 배포 자료라는 점은 사용자 확인으로 기록했다. 이 3건의 대조가 CSV 전체의 추출 이력이나 엑셀 전체의 품질을 검증한 것은 아니다.
- 식품 CSV의 원본 상세 다운로드 주소·입수일·추출 조건·해당 추출본의 이용조건은 아직 미확인이다. 관련 API 페이지의 이용조건을 그대로 적용하지 않는다. 출처 이력은 [등록부](research/DATA_SOURCES.md)에 유지한다.
- 현재 추출본에 없는 식품·제품을 다른 음식으로 대체하지 않는다. 주 데이터로 정한 보유 공식 엑셀을 전처리한 뒤 검색 범위를 다시 확인한다.

`validate`는 가공한 5만 행의 식별자·이름·단위·위치·영양소·결측을 원본과 대조하고, 검색·환산·오류 사례 17개를 확인한다. 원자료의 영양값 자체가 외부 기준과 맞는지, 실제 앱·챗봇이 같은 응답을 하는지는 별도 검증 대상이다.

# 일반 지식 챗봇 1차 연결

질문 → 인증·AI 처리 안내 확인 → 자료 검색 → 로컬 모델 호출 → 답변·출처 표시 흐름을 구현했다. 현재 검색 원본은 `docs/research/chatbot_replacement_v1/knowledge.json`의 대체 FAQ 13개다. NIDDK 교육자료 2종·CC BY 4.0 영양 권고문·식약처 고시 규범 본문을 연결했다. 이전 `chatbot_v5` 자료는 보관하며 현재 검색·모델 요청에는 넣지 않는다. LangChain이나 벡터 DB를 추가하지 않고 키워드 검색을 첫 기준선으로 사용한다. 아래 실제 모델 연결 기록은 당시 버전의 확인이며, 새 자료의 의학적 승인이나 실제 모델 재평가 완료를 뜻하지 않는다.

## 현재 범위

- 현재 질문·선택한 공개 지식과 같은 방의 최근 일반 대화 최대 2쌍(4개 메시지·1,500자)을 모델에 전달한다. 별도 저장·AI 처리 동의 후 대화방에 질문과 답변을 보관한다. 브라우저 영구 저장소에는 대화를 복사하지 않는다. 모델 서버 자체의 로그 정책은 별도로 확인해야 한다.
- 개인 혈당·식사 기록, 계정 번호·이메일·메모·저장된 공복 요약을 모델 요청에 넣지 않는다. ‘공복 기록 요약’ 버튼은 별도 조회·저장 동의 후 서버가 계산한 최근 7일 통계를 대화방에 보관하며 모델을 호출하지 않는다. 음식 영양 DB 조회는 미연결이다.
- 모델이 반환한 출처 ID를 검색 결과와 대조하고, 링크·발행기관·문서 절/고시 조항·저자 및 이용조건·한국어 재구성 사실을 서버가 관리하는 자료에서 표시한다. 웹문서에 PDF 쪽수를 만들어 붙이지 않는다. 출처가 없으면 정보 부족 안내로 처리한다.
- 질문 길이, 요청 출처, 사용자 인증, AI 처리 확인, 동시 요청, 시간 제한, 모델 응답 크기와 형식을 검사한다. 일반 대화는 닫기·페이지 이동 후에도 보존하고 새로고침·재로그인 시 서버에서 복원한다. 로그아웃·계정 변경은 이전 계정의 화면 상태를 지운다. 진행 중 공복 요약은 동의 해제·닫기·페이지 이동으로 취소할 수 있지만 이미 저장된 요약을 삭제하지는 않는다.
- 질문의 위험 표현 처리는 제한적인 규칙이며 검증된 의료 위험 분류기가 아니다. 출처 ID의 일치가 답변 내용의 사실성이나 임상적 정확성을 보장하지 않는다.
- 운동 자료는 운동·걷기·벽밀기·팔 들기 등의 활동 문맥이 있는 질문에서만 검색한다. `혈당 수치`·`합병증`·`30분`·`실내`만 겹친다고 운동 자료를 답변 근거로 사용하지 않는다. 현재 실내 예시는 벽밀기·팔 들기이며 자전거·탄력밴드의 사용법 질문을 이 자료로 답하지 않는다. 현재 자료에는 합병증 전반을 직접 설명하는 문항이 없으므로 일반 합병증 질문에는 근거 부족을 안내한다.
- 개인 수치를 적은 표현은 검색 전에 범위를 제한한다. 혈당 수치·값·측정 결과, 당화혈색소/HbA1c, 소수·전각 숫자를 구분하며 일반적인 기간 질문은 유지한다. 자유 질문에서 개인 기록을 자동 조회하지 않으며 공복 요약 버튼과 별도 동의를 안내한다. 개인 수치 해석과 맞춤 식단 추천도 제한한다. 이 규칙이 모든 표현을 인식하는 것은 아니다.

## 자료의 승인 상태

새 대체 자료집도 `runtime_publishable=false`와 초안 상태다. 자료 교체를 의료 내용·팀·공개 서비스 승인으로 기록하지 않았다. 기본 설정과 프로덕션 Supabase 모드에서는 이 자료로 답변하지 않는다.

로컬 시연의 `ASSISTANT_ALLOW_DRAFT_PREVIEW=1`은 개발 중 검색·연결을 확인하는 선택이다. `APP_MODE=demo` 또는 별도로 제한한 로컬 Supabase 개발 평가에서 적용되며 화면에 미리보기임을 표시한다. Supabase 평가는 개발 모드·loopback 요청·현재 서비스 동의·서버 허용 목록·`.invalid` 가상 계정을 모두 요구한다. 프로덕션에는 적용되지 않으며 실제 서비스 승인을 대신하지 않는다. [평가 실행 방법](ASSISTANT_SUPABASE_EVAL.md)과 [실제 Auth·DB·모델 평가 결과](research/assistant-supabase-eval/REPORT.md)를 참고한다.

운영 검색에는 자료집 게시 허용·내용/출처 검토, 문항의 승인일·유효한 재검토 기한, 출처의 재사용 허용 및 내용 해시가 필요하다. 원본 JSON을 변경해 승인 절차를 건너뛰지 않는다.

## 이 PC에서 연결하기

현재 이 PC는 Ollama 기본 서버 `127.0.0.1:11434`와 로컬 등록 모델 `team4-gemma4-e4b-qat:latest`를 사용한다. [Ollama 등록·연결 안내](ASSISTANT_OLLAMA.md)에 기존 GGUF 가져오기, 환경 설정과 실제 평가 방법을 정리했다. 아래 예시는 다른 호환 서버에도 적용하는 일반 연결 방법이며, 뒤의 LM Studio·11480 기록은 당시 실행 결과다.

[최종 Ollama 검증](research/assistant-eval-replacement40/OLLAMA_REPORT.md)은 무가당의 세부 기준 누락 보완, 고정 40문항, 모델 언로드 후 첫 요청, 실제 Supabase·팀 시연을 포함한다. [팀 실행 안내](ASSISTANT_TEAM_SETUP.md)에 현재 지원 범위와 초안 자료 상태를 정리했다.

별도로 실행한 모델 서버가 `POST /v1/chat/completions`를 지원해야 한다. `ASSISTANT_MODEL_RESPONSE_FORMAT`은 기본 `json_object`이며 이 옵션을 거부하는 LM Studio에서는 `text`를 사용한다. 두 설정 모두 모델에게 JSON 답변을 요구하고 서버에서 JSON·출처 ID를 엄격하게 검증한다. 앱은 모델을 다운로드하거나 GPU에 로드하지 않는다. 현재 연결부는 loopback 주소만 허용한다.

요청에는 `chat_template_kwargs: {enable_thinking: false}`와 `reasoning_effort: "none"`을 지정한다. 검색 근거의 완전한 출처 ID 목록과 출력 예시를 명시하며, 모델이 이를 줄여 쓰거나 없는 ID를 만들면 답변을 차단한다. 최초 llama.cpp 서버에서는 JSON Schema의 grammar 초기화가 실패했으므로 JSON 지시와 서버의 엄격한 사후 검증을 사용한다.

검색 요약에는 자료의 제목·주제도 함께 전달한다. 프롬프트는 질문에 직접 답할 내용만 사용하고, 관련 단어가 있다는 이유로 다른 주제로 넘어가지 않으며, 답할 근거가 없으면 출처를 비우도록 지시한다. 이 지시 자체는 모델의 준수를 보장하지 않으므로 실제 답변 평가는 별도로 필요하다.

모델 서버 주소와 모델 이름을 확인한 뒤 `.env.local`에 다음을 설정한다. 비밀키는 Git에 올리지 않는다.

```dotenv
ASSISTANT_ENABLED=1
ASSISTANT_MODEL_BASE_URL=http://127.0.0.1:8080/v1
ASSISTANT_MODEL=실제_서버의_모델_이름
ASSISTANT_MODEL_API_KEY=
ASSISTANT_MODEL_RESPONSE_FORMAT=json_object
ASSISTANT_ALLOW_DRAFT_PREVIEW=1
```

```powershell
npm run dev:demo
```

서버 설정 후 앱을 다시 실행하고 가상 계정으로 로그인한다. 도우미에서 AI 처리 안내를 확인한 다음 `당화혈색소가 무엇인가요?`를 입력한다. 모델 연결이 없으면 준비 중 또는 연결 오류를 표시하며, 미리 작성한 답을 실제 모델 응답으로 대신 보여주지 않는다.

## 파일과 API

- `src/lib/assistant/knowledge.ts`: 자료 승인·해시 검사, 키워드 검색, 출처 구성.
- `docs/research/chatbot_replacement_v1/knowledge.json`: 현재 런타임 검색 원본. FAQ 문안과 출처 등록부에서 `python scripts/prepare_assistant_replacement.py`로 생성하고 `--check`로 내용·입력 해시 일치를 확인한다.
- `src/lib/assistant/model.ts`: 로컬 호환 API 호출, 시간/크기 제한, 답변·출처 ID 검사.
- `src/lib/assistant/service.ts`: 입력·범위 확인, 질문 처리, 동시 요청 제한.
- `src/lib/assistant/answer-conditions.ts`: 인용한 기존 요약의 일부 필수 확인 항목이 누락되면 출처 요약으로 보충. 의학적 정확성 판정은 아니다.
- `GET /api/assistant`: 인증 후 사용 가능 상태만 반환. 모델 주소나 키를 공개하지 않는다.
- `POST /api/assistant`: `{question, allow_model_processing: true}`만 받는다. `user_id`·임의 모델 주소·대화 기록을 받지 않는다.
- `POST /api/assistant/records-summary`: `{allow_record_access: true}`만 받는다. 본인 최근 7일 공복 통계 전용이며 AI 처리 동의·모델 연결은 필요하지 않다. 현재 서비스 동의와 요청별 기록 조회 동의는 필요하다.
- `GET/POST /api/assistant/conversations`: 본인 대화방 목록 조회·명시적 보관 동의 후 생성.
- `GET/DELETE /api/assistant/conversations/[id]`: 본인 대화 복원·전체 삭제.
- `POST /api/assistant/conversations/[id]/turns`: 버전·질문 ID·AI 처리 동의를 확인하고 질문·답변을 저장. 이전 대화는 서버에서 읽으며 요청 본문의 이력은 거부한다.
- `POST /api/assistant/conversations/[id]/summaries`: 버전·요약 ID·기록 조회 및 저장 동의를 확인하고 계산된 통계와 조회 시각을 저장. 기존 단일 요청 API는 평가 도구 호환을 위해 유지한다.
- `src/components/assistant/assistant-widget.tsx`: 질문 전송, 답변·출처, 오류, 취소 및 초기화.

## 검증 범위

대체 자료집 전용 40문항은 `docs/research/assistant-eval-replacement40/cases.json`에 있다. 기존 40문항·20문항과 실행 결과는 보존했다. 새 평가본은 같은 질문을 재사용하는 회귀 평가이며 독립 검증 세트가 아니다. X02의 활동 예시와 X06의 기구 사용법 미지원 등 기대 결과 변경을 파일에 명시했다. 평가 러너의 기본 자료집·출처 검증도 새 자료를 사용한다.

```powershell
python scripts/prepare_assistant_replacement.py --check
python scripts/evaluate_assistant.py
```

```powershell
npm run check
npx playwright test tests/e2e/assistant.spec.ts tests/e2e/assistant-shell.spec.ts
```

Playwright 브라우저가 없고 Chrome이 설치된 PC에서는 먼저 PowerShell에서 `$env:PLAYWRIGHT_BROWSER_CHANNEL='chrome'`을 설정해 설치된 Chrome으로 실행할 수 있다.

단위 테스트는 자료 승인·변조·만료, 검색 기준선, 개인 요청의 범위 제한, 출처 위조, 취소, 로컬 HTTP 모의 서버와의 호환을 확인한다. 브라우저 테스트는 실제 앱의 인증/출처 검사와 모의 답변을 이용한 화면·동의·초기화를 확인한다. E2E 실행에서는 실제 모델 호출을 비활성화한다.

1차 구현 검증: `npm run check`의 lint·타입 검사·단위 테스트 46개·격리 SQL 70개·비 AI SQL 62개·계정 삭제 18개·프로덕션 빌드가 통과했다. 설치된 Chrome으로 위 브라우저 테스트 7개도 통과했고, 360px 답변 화면과 기본 비활성 모드의 360/768/1280px 접근성 검사를 확인했다. 당시에는 모의 응답을 사용했다. 로그는 로컬 `.tmp/research/assistant-check.log`, `.tmp/research/assistant-e2e.log`, 화면은 `.local/playwright-results/`에 있다.

## 첫 실제 모델 연결 확인 (11480)

사용자가 실행한 `http://127.0.0.1:11480/v1`을 연결했다. 모델 서버를 재시작하거나 로딩 설정을 바꾸지 않았다. 로컬 `.env.local`에 실제 `/v1/models`의 모델 ID를 저장했으며 Git에서는 제외한다.

당시 앱은 `http://127.0.0.1:3000`의 로컬 가상 계정 모드로 실행했다. 빌드한 앱을 다시 실행하려면 프로젝트 루트에서 다음 명령을 사용한다. 환경 파일을 명시적으로 읽으므로 모델 연결 설정도 적용된다.

```powershell
npm run build
node --env-file-if-exists=.env.local scripts/run-demo.mjs --production
```

가상 계정으로 실제 앱 API에서 다음을 확인했다.

- 당화혈색소·무가당 표시·과일과 주스 질문 3개: 실제 모델 답변과 해당 지식의 출처 ID·링크·PDF 페이지 확인.
- 개인 혈당 변화·인슐린 용량·관련 없는 날씨 질문 3개: 각각 범위 제한·안전 안내·근거 부족 처리.
- 비로그인 차단·AI 처리 동의 확인·개발용 미리보기 상태 및 캐시 금지: 3개 확인.

## 스크린샷의 검색 오류 수정 및 LM Studio 재연결

2026-10-22 사용자가 확인한 네 화면 중 `식전 혈당 수치가 140이 나왔어`와 `당뇨병 합병증은 뭐가 있어?`에 운동 자료가 잘못 연결됐다. 개인 수치 표현의 판별을 보완하고 운동 문맥이 없는 질문에서 운동 자료를 제외했다. 일반 당화혈색소 설명과 실제 운동 질문의 검색은 유지한다. 식단·개인 기록·개인 수치의 범위 제한 문구도 구분했다.

사용자가 모델을 다시 로드한 62121 포트는 LM Studio가 실행한 `llama-server.exe`의 내부 포트였고, `/v1/models`가 401을 반환했다. `lms server status --json`에서 외부 API 서버가 꺼져 있는 것을 확인한 뒤 `lms server start --port 1234 --bind 127.0.0.1`로 로컬 API만 시작했다. 모델 로딩이나 설정은 변경하지 않았다. `/v1/models`와 `lms ps --json`으로 로드된 `gemma-4-e4b-it-qat`를 확인했다.

이 LM Studio 서버는 `json_object`에 400을 반환하며 `json_schema` 또는 `text`만 허용한다고 응답했다. 이전 서버의 schema grammar 오류를 우회하기 위해 schema를 강제하지 않고 명시적인 `text` 모드와 기존 JSON·출처 사후 검증을 사용한다. 로컬 `.env.local`의 연결값은 다음과 같으며 Git에서 제외한다.

```dotenv
ASSISTANT_MODEL_BASE_URL=http://127.0.0.1:1234/v1
ASSISTANT_MODEL=gemma-4-e4b-it-qat
ASSISTANT_MODEL_RESPONSE_FORMAT=text
```

이 서버에서는 `chat_template_kwargs`만 보낸 요청에 추론 토큰이 발생해 출력 512 tokens 중 472 tokens를 사용했고, JSON 답변이 `finish_reason=length`로 잘렸다. 요청에 `reasoning_effort: "none"`을 함께 지정한 뒤 동일한 질문에서 추론 토큰 0·완전한 JSON·유효한 출처 ID를 확인했다. 잘린 답변을 허용하거나 형식 검사를 완화하지 않았다. 초기 11480 서버의 시간초과 원인이 밝혀진 것은 아니다.

연속된 실제 요청에서는 LM Studio가 HTTP 400과 `Engine protocol predict request failed: fetch failed`를 반환하는 현상도 재현했다. 해당 오류 문자열이 명시된 경우에만 같은 취소 신호·30초 제한 안에서 요청을 한 번 더 보낸다. 두 번째 요청도 실패하면 연결 오류를 반환하며, 다른 HTTP 오류·시간초과·취소·답변 형식/출처 오류에는 재시도하지 않는다. LM Studio 내부 연결 실패의 근본 원인은 확인하지 못했다. 앱에서는 텍스트 생성만 요청하며 도구 실행이나 개인 기록 쓰기는 하지 않는다.

수정 후 lint·타입 검사·단위 테스트 51개·프로덕션 빌드를 통과했다. 빌드한 앱 API에서 스크린샷의 네 질문과 정상적인 운동 질문을 순서대로 확인해 5개 모두 예상한 응답을 받았다. 당화혈색소·운동 질문 2개는 실제 모델 답변과 유효한 출처를 반환했고, 나머지 3개는 범위 제한/근거 부족으로 처리했다. 실제 360px 브라우저에서도 제한 안내 3개를 확인했다. 실제 모델을 비활성화한 브라우저 회귀 검사 7개도 통과했다. 원본 자료의 승인 상태는 변경하지 않았으며, 이번 수정에서 DB 구조나 집계 계산은 변경하지 않았다. 로그·원인 진단·화면은 로컬 `.tmp/research/assistant-query-fix/`에 보관한다.

## 답변 말투와 길이 개선

일반 지식 챗봇과 검색 오류 수정까지를 로컬 커밋 `388f747`에 보존한 뒤, 같은 8개 질문으로 문체 변경 전후를 비교한다. 모델·검색·숫자 계산·출처 검증·기능 범위는 유지한다.

## 최근 7일 공복 기록 요약

`src/lib/assistant/record-summary.ts`는 서버가 확인한 사용자와 기간만 사용한다. 기간은 한국시간 오늘을 포함한 7개 날짜이며 오늘은 조회 시각까지다. 날짜 시작은 포함하고 다음 날 자정은 제외한다. ‘공복’만 선택하고 기상 직후·식전·식후 기록을 섞지 않는다. 미래 측정 시각과 타인 기록도 제외한다.

평균은 측정 건수 기준이며 소수 첫째 자리까지 반올림한다. 같은 날 여러 건은 각각 한 건이다. 기록 건수·기록 일수·미기록 일수·평균·최솟값·최댓값을 반환하고, 빈 기록의 수치는 `null`이다. 미기록일을 0으로 보간하지 않는다. 측정 당시 실제 공복 여부를 검증하거나 정상·호전·원인을 판단하지 않는다.

이 첫 단계는 **AI로 해석하는 개인화 챗봇이 아니라 서버 계산 결과를 도우미 안에서 보여주는 기능**이다. 모델에 원기록이나 통계·메모·계정 식별자를 보내지 않는다. 의학 출처 인용과 구분하여 ‘본인 혈당 기록’을 출처로 표시한다.

기존 단일 요청 API는 계산 결과만 반환한다. 화면의 대화방 요약은 별도 조회·저장 동의 후 통계와 조회 시각을 보관한다. 기록 조회 전후 인증·서비스 동의를 확인한다. 체크 해제·닫기·페이지 이동·로그아웃·계정 변경은 진행 중 요약을 취소하고 기록 조회 동의를 초기화하지만 이미 저장된 요약은 유지한다. 기록 변경 시 다른 탭에서도 패널을 닫고 동의를 초기화하며, 저장된 요약에는 조회 당시의 값임을 표시한다. 새로 요약하면 새로운 시점의 결과가 추가된다. 대화방 삭제는 그 방의 모든 질문·답변·요약을 삭제하고, 원래 혈당 기록은 유지한다.

별도 실제 API·브라우저 검사: `npx playwright test --config playwright.summary.config.ts`. 새 가상 데이터 파일을 사용하고 초안 검색과 모델 호출은 끈다. 기존 40문항은 유지하며 추가 20문항과 최초 실패·재평가는 [추가 평가 보고서](research/assistant-eval-new20/REPORT.md)에 구분한다.

이번 구현의 최종 검증은 단위 65개·SQL 70/62개·계정 삭제 18개·빌드·기존 브라우저 7개·실제 공복 요약 API/브라우저 5개 통과다. 추가 20문항은 자동 20/20·내용 18/20이며 기구 안정성에 관한 2개 기대는 근거 범위와 함께 후속 항목으로 남겼다. 기존 40개는 자동 40/40·적용 가능한 내용 38/38, 미연결 전제가 바뀐 P01/P02 2개는 범위 변경으로 별도 표시했다. 일부 조건 누락은 인용한 기존 요약으로 서버가 보충하므로 모델 단독 성적이나 임상 승인으로 해석하지 않는다.

## 대체 근거자료의 실제 평가 — 2026-10-23

대체 자료집 `replacement-v1-draft-1`과 사용자가 로드한 `gemma-4-e4b-it-qat`로 40문항을 실제 실행했다. 자동 검사는 40/40, 최종 앱 응답의 내용 검토는 적용 가능한 38개 중 36개 충족·2개 미충족이다. P01·P02는 실행 전에 확인한 기능 전제 변경으로 별도 표시했다. 출처가 포함된 생성 답변은 16개이며, 그중 N03 1개는 서버의 기존 출처 요약 보충을 포함한다.

미충족은 B03의 메모로 혈당 변화 원인을 증명할 수 없다는 한계 누락과 N02의 무당·무가당 구분 누락이다. 이번 고정 질문에서는 안전 안내·접근 제한이 예상대로 동작했고 생성 답변을 반환한 요청의 앱 응답 시간 중앙값은 833ms였다. 앱 코드·자료집·문항을 고치지 않은 최초 결과이며 모델 단독 성능·독립 검증·의료 승인이 아니다. [전체 결과와 후속 수정 항목](research/assistant-eval-replacement40/REPORT.md), [40개 답변 원문과 판정](research/assistant-eval-replacement40/runs/20261023-replacement-baseline/RESPONSES.md)을 확인할 수 있다.

## 대체 자료 답변 누락 보완 — 2026-10-23

B03의 메모로 원인을 증명할 수 없다는 한계를 요약·프롬프트·누락 검사에 유지했다. N03은 무가당의 제조 조건과 무당의 함량 기준, 정확한 0을 보장하지 않는다는 한계를 유지한다. 이 두 설명이 불완전하면 실제 인용한 요약으로 대체하며, 상충하는 생성 문장을 함께 표시하지 않는다. 탄수화물의 식이섬유·섭취량과 새 활동 전의 활동 능력·복약·식사 계획·기존 제한도 확인한다. `영양사`의 `양`을 섭취량 설명으로 잘못 인식하던 검사를 고쳤다.

최종 단위 테스트 69개·lint·타입 검사·빌드가 통과했다. 같은 모델·생성 설정과 고정 40문항에서 최종 자동 40/40·적용 가능한 내용 기준 38/38을 충족했다. 기능 전제가 바뀐 2개는 별도이며 출처가 포함된 생성 답변은 15개다. N05·X02 2개는 요약 대체·보충을 포함하므로 모델 단독 성적이 아니다. 자료집은 `replacement-v1-draft-3`이며 최초·중간 실패와 최종 원문은 [보완 보고서](research/assistant-eval-replacement40/HARDENING_REPORT.md)에 보존했다.

## 공복 요약의 수정·삭제 반영 검증 — 2026-10-23

누락 보완을 `92b8ce0`에 커밋한 뒤 로컬 가상 계정에서 두 탭을 열어, 수치 수정·공복에서 식전으로 변경·삭제 후 기존 요약과 조회 동의가 지워지고 재조회 통계가 맞는지 검증했다. 배경 대시보드·기록 목록에 이전 데이터가 남는 오류를 발견해 조회 훅이 기존 기록 변경 알림을 구독하도록 보완했다. 수정 전 집중 검사 실패와 수정 후 전체 통과를 보존했다. 브라우저 시나리오 6개·단위 테스트 69개·격리 SQL 70/62개와 계정 삭제 SQL 18개·lint·타입 검사·빌드가 통과했다. 모델 설정·서버 집계·DB 스키마는 바꾸지 않았다.

위 결과는 로컬 demo 저장소·별도 PGlite 검사다. 이후 사용자가 만든 별도 Supabase 테스트 프로젝트를 이 PC에 연결해 실제 Auth·SSR 쿠키·PostgREST·RLS와 기록 변경 흐름을 확인했다. 실제 DB에서 7개 시나리오 그룹이 통과했고, 직접 PostgREST 요청으로도 다른 계정의 기록 조회·수정·삭제·추가가 차단됐다. 360px 브라우저 두 탭에서 수치·측정 상황 변경·삭제 후 요약과 대시보드 갱신, 다른 탭 로그아웃도 확인했다.

실제 검증은 `npm run dev -- --webpack --port 3005`로 실행했다. 기본 Turbopack 개발 서버의 반복 새로고침과 첫 Webpack 검사에서 변경 알림 처리가 끝나기 전에 도우미를 다시 열어 발생한 검사 실패도 보존했다. 마지막 검사는 변경된 대시보드 행을 확인한 뒤 도우미를 열었으며 제품 코드는 추가 수정하지 않았다. 테스트용 혈당 기록은 정리했다. 일반 건강정보 모델 답변은 Supabase 모드의 자료 승인 조건을 유지하며, 이번에는 모델 추론을 실행하지 않았다. 확인 메일의 기본 복귀 주소인 Site URL은 `http://127.0.0.1:3005`로 저장하고 페이지를 새로 불러온 뒤 유지되는 값을 확인했다. 실제 회원가입·확인 메일 수신과 운영 배포는 별도 확인 대상이다. [실제 DB 결과·최초 실패·화면·검증 범위](research/assistant-record-summary-validation/REPORT.md)에 상세를 구분했다.
